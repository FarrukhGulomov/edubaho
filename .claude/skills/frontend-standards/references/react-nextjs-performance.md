# React / Next.js — производительность

> Читается агентом при вопросах производительности, ревью React/Next.js кода, оптимизации бандла или данных.
> Таксономия категорий и приоритетов основана на открытом (MIT) наборе правил Vercel Engineering «react-best-practices» (github.com/vercel-labs/agent-skills) — ниже переработанное и сокращённое изложение своими словами, с собственными примерами, адаптированное под наш стек (TanStack Query, Zustand/RTK, styled-components, FSD).

Порядок ниже — по убыванию приоритета. Если правки конфликтуют — выше приоритет побеждает.

## 1. Устранение waterfalls (критично)

Самая дорогая проблема производительности — последовательные, а не параллельные асинхронные операции.

- Проверяй дешёвые синхронные условия до `await` дорогих/удалённых значений — не жди фичефлаг или сессию, если результат всё равно решится синхронной проверкой.
- Не `await` то, что не нужно немедленно — двигай `await` внутрь ветки, где значение реально используется.
- Независимые запросы — через `Promise.all`, а не последовательные `await`.
- Если часть операций зависима, а часть нет — не сериализуй всё целиком, группируй независимое.
- В API-маршрутах/server actions — стартуй промисы как можно раньше, `await` — как можно позже.
- Для потоковой отдачи медленных секций страницы — используй `Suspense`/стриминг вместо ожидания всего дерева.

```tsx
// плохо — последовательно
const user = await getUser(id);
const orders = await getOrders(id);

// хорошо — параллельно
const [user, orders] = await Promise.all([getUser(id), getOrders(id)]);
```

## 2. Размер бандла (критично)

- Импортируй напрямую из конкретного модуля, избегай barrel-файлов (`index.ts`, реэкспортирующих десятки модулей) — они тянут в бандл лишнее и ломают tree-shaking.
- Пути импортов/файлов должны быть статически анализируемыми (без динамически собранных строк) — иначе бандлер не сможет посчитать зависимости и включит слишком много кода.
- Тяжёлые компоненты (графики, редакторы, модалки с большими зависимостями) — грузить через динамический импорт (`next/dynamic` в Next.js, `React.lazy` в чистом React), не в основной чанк.
- Аналитику/логирование сторонних SDK — подключать после гидратации, не блокируя первый рендер.
- Модули для фич за флагом — грузить только когда фича реально активирована.
- Для интерактивных действий — предзагружать код по hover/focus, чтобы клик ощущался мгновенным.

## 3. Серверная производительность (высокий приоритет)

- Server actions аутентифицировать так же строго, как обычные API-роуты — они не «безопаснее по умолчанию».
- Дедуплицировать одинаковые запросы в рамках одного запроса (кэш на уровне рендера RSC/SSR), чтобы одни и те же данные не запрашивались с сервера повторно за один HTTP-запрос.
- Для кэша между запросами — использовать LRU/serverless-совместимый кэш, а не module-level переменную без TTL.
- Не сериализовать в клиентские компоненты больше данных, чем реально нужно для рендера — минимизируй payload.
- Статичный I/O (шрифты, лого, конфиги) — поднимать на уровень модуля, а не читать на каждый рендер.
- Не хранить мутируемое состояние запроса в module-level переменных на сервере — в serverless/edge среде это течёт между запросами.
- Компоненты, которым нужны данные с сервера, реструктурировать так, чтобы независимые фетчи шли параллельно, а не по цепочке `await` внутри дерева.
- Для списков с фетчем на каждый элемент — собирать вложенные запросы в один `Promise.all`, а не await поэлементно в цикле.
- Неблокирующие побочные эффекты (логирование, аналитика после ответа) — выносить в фоновые задачи после отправки ответа, а не задерживать сам ответ.

## 4. Клиентский фетчинг данных (средне-высокий приоритет)

В нашем стеке за это отвечает **TanStack Query** (см. `AGENTS.md`/`docs/ARCHITECTURE.md`, раздел «Управление состоянием»):

- TanStack Query уже даёт дедупликацию одинаковых запросов и кэш «из коробки» — не оборачивай его вручную своим кэш-слоем поверх.
- Глобальные обработчики событий (resize, scroll, visibility) — подписывать один раз на приложение, а не по одному на каждый использующий их компонент.
- Для скролл-обработчиков — использовать passive-слушатели, чтобы не блокировать скролл ожиданием обработчика.
- Данные в `localStorage`/`sessionStorage` — версионировать (схема + номер версии) и хранить по минимуму, не как основной источник истины.

## 5. Оптимизация ре-рендеров (средний приоритет)

- Не подписывайся на кусок состояния, который используется только внутри колбэка, а не в самом рендере, — это вызывает лишние ре-рендеры.
- Дорогие вычисления/тяжёлую разметку — выносить в отдельный мемоизированный компонент (`React.memo`), а не мемоизировать значение прямо в родителе.
- Непримитивные пропы по умолчанию (объекты, массивы) — поднимать в константу вне компонента, а не создавать заново при каждом рендере.
- В зависимостях `useEffect`/`useMemo`/`useCallback` — использовать примитивные значения, а не целые объекты, если реально меняется только одно поле.
- Подписываться на производное булево (`isEmpty`, `hasChanges`), а не на весь массив/объект, если важен только этот факт.
- Производное состояние вычислять прямо при рендере, а не через `useEffect` + дополнительный `useState`.
- Функции обновления состояния — через функциональную форму `setState(prev => ...)`, чтобы колбэк не зависел от актуального значения и оставался стабильным.
- Дорогую начальную инициализацию `useState` — передавать функцией (`useState(() => expensiveInit())`), а не вызывать сразу при каждом рендере.
- Не мемоизировать тривиальные примитивные выражения — овcemоверхед мемоизации может быть дороже самого вычисления.
- Если у одного `useEffect`/хука несколько независимых зависимостей и назначений — разделять на несколько простых, а не один комбинированный.
- Логику, которая должна сработать «по действию пользователя», размещать в обработчике события, а не в эффекте, реагирующем на изменение состояния.
- Немедленные, но не срочные обновления UI — через `startTransition`, чтобы не блокировать более приоритетный ввод.
- `useDeferredValue` — чтобы дорогой рендер (например, длинный список по поисковому запросу) не блокировал отклик поля ввода.
- Часто меняющиеся, но не влияющие на разметку значения — держать в `ref`, а не в состоянии, вызывающем ре-рендер.
- Не объявлять компоненты внутри других компонентов — новый компонент на каждый рендер размонтирует и заново монтирует поддерево.

## 6. Производительность рендеринга (средний приоритет)

- Анимировать оборачивающий `div`, а не сам `SVG`-элемент — так плавнее и дешевле для браузера.
- Для длинных списков — `content-visibility: auto`, чтобы браузер не считал layout для оффскрин-контента.
- Статичный JSX, который не зависит от пропов/состояния, — выносить константой вне компонента, а не пересоздавать при каждом рендере.
- Точность координат в SVG — уменьшать до разумного минимума, а не хранить лишние знаки после запятой.
- Данные, доступные только на клиенте (например, из `localStorage`), выводить через инлайн-скрипт до гидратации, чтобы избежать визуального мигания.
- Ожидаемые (осознанные) расхождения серверного/клиентского рендера — подавлять точечно (`suppressHydrationWarning`), а не игнорировать предупреждение целиком.
- Для показа/скрытия целых поддеревьев без потери состояния — рассмотреть `Activity`/аналоги вместо условного размонтирования.
- Условный рендеринг — через тернарный оператор, не через `&&` (см. `docs/CODE_STYLE.md`).
- Индикатор загрузки — предпочтительно через `useTransition`, а не отдельный ручной флаг состояния.
- `<script>` — с `defer`/`async`, если скрипт не нужен для первого рендера.

## 7. JavaScript-микрооптимизации (низкий-средний приоритет)

Точечные приёмы, важны в горячих путях (циклы по большим массивам, частые ре-рендеры), не имеет смысла применять «на всякий случай» к редко исполняемому коду:

- Группировать изменения стилей через CSS-класс/`cssText`, а не по одному свойству за раз.
- Для повторяющихся поисков по коллекции — строить `Map`, а не искать линейно каждый раз.
- Кэшировать доступ к свойствам объекта внутри циклов в локальную переменную.
- Результаты чистых, но дорогих функций — кэшировать в module-level `Map`.
- Чтения из `localStorage`/`sessionStorage` — кэшировать в памяти, не читать при каждом обращении.
- Несколько последовательных `filter`/`map` над одним массивом — по возможности объединять в один проход.
- Перед дорогим сравнением — сначала проверять дешёвое условие (например, длину массива).
- Из функций — выходить рано (`early return`), а не вкладывать логику в глубокий `if`.
- Создание `RegExp` — выносить из цикла наружу.
- Для поиска минимума/максимума — проходить массив циклом, а не сортировать целиком.
- Для проверки принадлежности — `Set`/`Map` (O(1)), а не `Array.includes` (O(n)) на горячем пути.
- Для иммутабельной сортировки — `toSorted()`, а не мутирующий `sort()` с ручным копированием.
- `map` + `filter` в одной операции — через `flatMap`, где это уместно.
- Некритичную фоновую работу — откладывать через `requestIdleCallback`.

## 8. Продвинутые паттерны (низкий приоритет)

- Результат `useEffectEvent` не класть в зависимости эффекта — он для того и существует, чтобы не быть зависимостью.
- Обработчики событий, которым нужен доступ к последним пропам/состоянию без пересоздания подписки, — хранить в `ref`.
- Инициализацию уровня приложения — выполнять один раз за загрузку приложения, а не при каждом монтировании компонента.
- Для стабильной ссылки на «последнее» значение внутри колбэка — паттерн `useLatest`.

---

## Как этим пользоваться

Не обязательно проверять каждый пункт на каждую строчку кода. Приоритет — как ориентир: сначала исключай waterfalls и раздутый бандл (эффект на пользователя самый заметный), нормализуй серверную часть и клиентский фетчинг, и только потом — точечные ре-рендер/JS-микрооптимизации, если для этого есть измеримая причина (профилировщик, реальная жалоба на тормоза), а не «на всякий случай».
