# Стандарты кода — JS/TS/React/CSS

> Читай при написании или ревью кода. Источник: соглашения Frontend Guild (Confluence) + общие принципы качества кода.

## 0. Главный принцип форматирования

**ESLint и Prettier — единственный источник истины по форматированию.** Всё, что ниже описывает форматирование (кавычки, отступы, длина строки), верно ровно до тех пор, пока не противоречит актуальному конфигу ESLint/Prettier проекта (обычно единый shared-конфиг пакетом, например `@org/eslint-config`). При конфликте между этим документом и конфигом — побеждает конфиг. Не спорить с линтером и не отключать правила инлайн без комментария с причиной и явного согласования.

Типовой эталонный конфиг:

```js
// eslint.config.mjs
import sharedConfig from "@org/eslint-config";
export default [sharedConfig];
```

Основа: `eslint:recommended`, `@typescript-eslint/recommended`, `react/recommended`, `react-hooks/recommended`, `jsx-a11y/recommended`, `import/recommended`, `prettier/recommended`. Частые кастомные правила: `unused-imports/no-unused-imports` (error), `max-len` (warn, ~100 символов), `@typescript-eslint/no-explicit-any` (warn), `react-hooks/exhaustive-deps` (warn).

## 1. Именование

- Имена отражают назначение, а не реализацию: `getUserByEmail`, не `fetchData2`.
- Булевые переменные — с префиксом: `isLoading`, `hasError`, `canEdit`.
- Обработчики событий: `handleSubmit` (метод компонента), `onUserSelect` (проп/колбэк наружу).
- Константы: `UPPER_SNAKE_CASE`, если значение действительно неизменное по смыслу (не просто `const`).
- Функции: глагол или глагольная фраза. Для однотипных операций — один и тот же глагол везде: `get`, а не вперемешку `get`/`retrieve`/`fetch` в одном проекте.
- Булевые проверки должны звучать как естественный язык в `if`: `isSedan`, `hasAirbag`, а не `sedan`, `airbag`.
- Классы и React-компоненты — `PascalCase` (`Car`, `UserCard`), экземпляры и обычные переменные — `camelCase`.
- Не сокращать имена ради экономии на нажатиях клавиш: `dueDate`, не `d`. Однобуквенные имена допустимы только для индексов циклов и очень маленьких стрелочных функций.
- Не использовать подчёркивание в начале имён внутренних методов (`_onClick` → `onClick`).

## 2. Структура функций и компонентов

- Одна функция — одна ответственность. Делает больше одного действия — разбить.
- Максимум ~40 строк на функцию (кроме деклараций конфигов/мапингов).
- Максимум 3 уровня вложенности — глубже выносить в подфункцию или использовать ранний `return`.
- Не дублировать логику — выносить в общую функцию.
- Не хардкодить магические числа — выносить в именованные константы.
- Вспомогательные функции, которым не нужны данные компонента, — выносить за пределы компонента (перед его определением), а не объявлять внутри рендера.
- Компонент разрастается и решает больше одной задачи → разбить на несколько компонентов. Признаки: >5 пропов, сложная разметка внутри условий/циклов.

## 3. TypeScript

- Каждый экспортируемый `interface`/`type`/`enum` документируется в формате JSDoc.
- Пропсы компонентов — через `interface`, по возможности расширяющий нативный HTML-элемент, если компонент оборачивает нативный тег:

```ts
interface IButtonProps extends ButtonHTMLAttributes<HTMLButtonElement> {
  /** Текст внутри кнопки */
  text: string;
  /** Функция, выполняемая после нажатия кнопки */
  action: () => void;
}
```

- `interface` и `type` в проекте функционально почти взаимозаменяемы — выбираем `interface` для форм объектов/пропсов по умолчанию (единообразие), `type` — для union/intersection и утилитарных типов.
- Типизировать состояние явно, особенно когда начальное значение может быть `null`:

```ts
const [user, setUser] = useState<IUser | null>(null);
```

- Дженерики — для переиспользуемых компонентов и функций (например, обёртки над списками).
- `any` — запрещён без явного комментария-обоснования; в конфиге это обычно `warn`, но в ревью считается замечанием, требующим исправления, если не обосновано.
- React-события типизировать через `React.MouseEvent<HTMLButtonElement>` и т.п., не `any`/`Event`.

## 4. React

**JSX и рендеринг**
- Булевые пропсы без `={true}`: `<Navbar showTitle />`, не `showTitle={true}`.
- Ветвление на 2 варианта — тернарный оператор; на 3+ варианта — объектный литерал/маппинг, не `switch` внутри JSX-логики.
- `<Fragment>`/`<>` вместо оборачивающего `div`, если обёртка не нужна семантически.
- Условный рендеринг — тернарный оператор (`cond ? <A /> : null`), избегать `&&` там, где левая часть может быть `0` (риск вывести `0` в разметку).
- Не создавать вложенные тернарники — извлекать в отдельный компонент/функцию с явными `if`.
- Списки — выносить `map()` в отдельный компонент списка, а не смешивать с остальной разметкой родителя.
- Многострочный JSX — оборачивать в скобки; компонент без children — самозакрывающийся тег.
- Строковые пропсы — без фигурных скобок: `title="My App"`, не `title={"My App"}`.
- Не оставлять JS-логику (side effects) прямо в JSX-обработчиках — выносить в именованный `handleX`.

**Компоненты**
- Функциональные компоненты + хуки — стандарт по умолчанию. Классовые компоненты — только если того требует существующий legacy-код.
- Компонент всегда именован (не анонимный `export default () => ...`) — упрощает стек-трейсы и профилирование.
- Один компонент — одна директория, с локальными файлами компонента, стилей, тестов; `index.ts` только реэкспортирует, не содержит реализации.
- Деструктуризация пропов в сигнатуре функции, а не обращение через `props.x`.
- Дефолтные значения пропов — через деструктуризацию (`{ title = '' }`), не через `Component.defaultProps`.
- Не плодить статическую разметку для списков/фильтров — выносить в конфигурационный массив объектов и маппить.
- `React.memo` — для компонентов, ре-рендер которых не зависит от часто меняющегося родительского состояния и есть измеримая проблема производительности (не преждевременная оптимизация «на всякий случай»; подробнее про ре-рендеры и другие перформанс-паттерны — `references/react-nextjs-performance.md`).
- Хуки предпочтительнее HOC и render-props для переиспользования логики.
- Группировка компонентов — по модулю/домену (см. `references/architecture-fsd.md`), не по техническому типу (`components/`, `containers/`).
- Сторонние UI-компоненты — не импортировать напрямую по всему проекту, оборачивать/реэкспортировать через `shared`, чтобы замена библиотеки не требовала правок по всей кодовой базе.
- Абсолютные импорты вместо длинных относительных путей (`features/auth` вместо `../../../features/auth`).
- Документировать компонент и его пропсы в JSDoc-формате (описание, `@example` для нетривиальных случаев).

**Порядок импортов:** встроенные модули → внешние пакеты → внутренние модули проекта (путь к внутренним — абсолютный, по правилам FSD).

## 5. CSS / styled-components

- Стилизация — через `styled-components`. Другие подходы (CSS-модули, SCSS, Tailwind) не «запрещены», но не являются стандартом проекта — использование по умолчанию не согласовывается отдельно, отклонение от styled-components — согласовывается.
- Styled-компоненты держим в одном файле с компонентом, который их использует. Выносим в отдельный `styled.ts`/`*.styles.ts` только когда стилизованных компонентов в файле становится много и они мешают читать основную логику.
- Не использовать инлайн-стили (`style={{ ... }}`) для постоянной стилизации — только для действительно динамических, вычисляемых значений, которые нет смысла заводить в styled-компонент.

## 6. Комментарии и документация в коде

- JSDoc — для всех экспортируемых функций, интерфейсов, enum, компонентов.
- Инлайн-комментарий объясняет **почему**, а не **что** делает код.
- `// TODO: ...` — только с описанием причины и, желательно, ссылкой на задачу.
- Не комментировать очевидное (`i++; // increment i`).

## 7. Полная таблица антипаттернов

| Антипаттерн | Что делать вместо |
|---|---|
| Магические числа | Именованные константы |
| Глубокая вложенность циклов/условий | Выносить в отдельную функцию, ранний `return` |
| Копипаст блока кода | Выносить в переиспользуемую функцию/компонент |
| `getUserData`, `fetchData2` | Точные, глагольные имена: `getUserByEmail` |
| `showTitle={true}` | `showTitle` |
| `switch` на 3+ ветки в JSX | Объектный литерал/маппинг |
| `div` вместо `Fragment` без надобности | `<>...</>` |
| Функция объявлена внутри рендера | Вынести `handleX` за пределы JSX |
| `cond && <X/>` при cond потенциальном `0` | Тернарный оператор |
| Вложенные тернарники | Отдельный компонент/явные `if` |
| Конкатенация строк (`+`) | Строковые литералы (template strings) |
| `Component.defaultProps` | Дефолты в деструктуризации пропов |
| Компонент без имени (`export default () => ...`) | Именованная функция компонента |
| Импорт сторонних UI-компонентов напрямую везде | Реэкспорт/обёртка через `shared` |
| Относительные импорты через несколько уровней (`../../../`) | Абсолютные импорты по правилам FSD |
| Группировка `components/` + `containers/` по типу | Группировка по модулю/домену (FSD) |
| `any` без комментария | Точный тип или обоснованный комментарий |
| Инлайн-стили для статичной стилизации | `styled-components` |
| God-компонент/god-файл | Разбить по ответственности |
| Отключение eslint-правила без комментария | Комментарий с причиной + согласование |
